# Contributing to isdb-rs

Thank you for helping. This file covers the rules that are specific to this
project (specifications as ground truth, RF safety, test data) and the
mechanics (toolchain, hooks, checks, commits). The crate map is in
[README.md](README.md#crates); the architecture (data flow, threads, the
frame and latency contract) is in [docs/architecture.md](docs/architecture.md).

## Ground rules

### The specifications are the only ground truth

- Behaviour is implemented from the published specifications listed in
  [SPECS.md](SPECS.md) (ITU-T H.222.0 | ISO/IEC 13818-1, ARIB STD-B10,
  STD-B21, STD-B24, STD-B31, STD-B32), in the editions given there.
- Other implementations (e.g. GNU Radio gr-isdbt, other TS libraries) are
  **not** references. Do not copy their code, tables or constants, and do not
  "fix" a disagreement by matching them. They may be run as independent
  oracles in differential tests (see [Oracle checks](#oracle-checks)); a
  disagreement is resolved by reading the spec.
- Every public item's doc comment names the clause or table it implements,
  e.g. `/// ARIB STD-B10 §5.2.6, Table 5-5`.
- Specification text is copyrighted and is **never committed**. Keep local
  extractions (`pdftotext -layout <pdf> specs/<name>.txt`) in the
  gitignored `specs/` directory. Short quotations in SPEC-NOTES entries are
  fine; whole tables or pages are not.

### Record every interpretation in SPEC-NOTES

When the spec text is ambiguous, garbled by PDF extraction or seemingly
inconsistent, add an entry to the `SPEC-NOTES.md` of the crate that
implements it (`crates/<crate>/SPEC-NOTES.md`; create it if the crate has
none and add it to the index in the top-level [SPEC-NOTES.md](SPEC-NOTES.md)).
Decisions that span crates go in the top-level file. Entry format:

```text
## <crate>: <topic>
- Spec: ARIB STD-B31 v2.2 §x.y, Table/Fig …
- Text: "…"
- Interpretation: …
- Confirmation: … (status: confirmed | pending real-world check)
```

Change an entry's status to `confirmed` only with evidence (a spec vector,
an oracle run, a real receiver or capture) and say which.

### Tests carry the proof

- Values printed in a spec (check values, tables, PRBS states, constellation
  points, frame lengths) are asserted directly; name such tests
  `spec_<table>_…`. Property tests are named `prop_…`.
- Decoders are lossless (reserved bits included): `encode(decode(x)) == x`
  is property-tested. Decoders return errors on malformed input; they do
  not panic.
- Each TX stage has its RX inverse tested as an identity.
- Committed fixtures are synthetic, generated by this project's own
  encoders.

### RF safety (hardware contributors)

Radiating on broadcast (UHF TV) frequencies requires a licence: in Japan
under the Radio Act (電波法), elsewhere under local law. Contributors who
run the transmit path on hardware must:

1. Use a **conducted or shielded** setup only: coax with attenuators straight
   into the receiver, or a shielded enclosure. No antenna on the TX port.
2. Check the settings first without radiating: `isdb tx --radio hackrf …
   --dry-run`, which prints the backend's settings and exits (`--radio`
   without `--rf-enable` or `--dry-run` is rejected).
3. Add `--rf-enable` only on that bench; start with a low TX gain
   (`--gain txvga=N` on a HackRF, a high `--gain att=N` on a Pluto) and
   leave the RF amplifier off (`--gain amp=on` is opt-in). Bound runs with
   `--seconds` where practical. A Pluto can be tested without radiating
   with `loopback=on` (TX LO powered down, digital TX→RX loopback).
4. Only transmit or relay content you have the rights to. The project does
   not descramble and refuses scrambled input; changes that add
   descrambling or conditional-access (B-CAS) support will not be accepted.

### Relay policy: copy control and conditional access

The `ts-program` relay (`isdb mux --relay`, `kind = "ts-program"` streams)
retransmits a recorded program, so changes to it must keep these rules:

- **Input must be unscrambled** (transport_scrambling_control '00' on every
  relayed packet). Scrambled input is refused, never descrambled.
- **Conditional-access signalling is kept by default.** The source
  program's CA_descriptor and ECM are carried into the output (`ca =
  "keep"`, the default); `ca = "drop"` removes them only when the user asks
  for it explicitly.
- **Copy control preserves the source by default.** The relayed service
  carries the source's digital copy control. A user may relax it only
  explicitly (`--copy`, `recording_control` in the TOML), and the source
  value is then reported as an `info` line so the change is visible.
- Keep these defaults and their tests when you touch the relay, and do not
  add paths that weaken them silently. The exact options are in
  [docs/mux-config.md](docs/mux-config.md) and
  [docs/transmitting.md](docs/transmitting.md).

Rules for code changes:

- Nothing may radiate without the explicit `--rf-enable` flag; keep every
  exit path stopping the stream and switching the amplifier off. The gate
  lives in `isdb-cli` and applies to every backend; `isdb-radio` backends
  must validate everything in `describe_tx` / `describe_rx` (what
  `--dry-run` prints) and open no device there.
- Tests, examples run by tests, and CI never open a radio device. Hardware
  checks are manual and are described in the PR (setup, attenuation,
  channel, gains).

### Real capture data never enters the repository

Captures, recordings, media and IQ files are never committed (`*.ts`,
`*.m2ts`, `*.cf32`, `*.cs8`, `*.cu8`, `*.iq`, the usual media formats and a
`media/` directory are gitignored). Tests that need
them read a path from an environment variable and print `SKIP` and pass when
it is unset or the file is missing, so a fresh checkout passes with no data:

| Variable | Points at |
|---|---|
| `ISDB_RS_CAPTURE_TS` | a terrestrial ISDB-T capture; the tests that parse PES payloads need them unscrambled (transport_scrambling_control '00') |
| `ISDB_RS_OUR_TS` | a TS produced by `isdb mux`, compared with the capture |
| `ISDB_RS_RELAY_TS` | an unscrambled recording (transport_scrambling_control '00') that you have the rights to relay (`ts-program`) |
| `ISDB_RS_MEDIA_DIR` | your own media: `video.m2v` (MPEG-2 video ES), `audio.m2a` (AAC ADTS); some tests also need `ffprobe` |

Which tests read which variable is listed in
[docs/test-data.md](docs/test-data.md) and in each crate's README. New
real-data tests must follow the same pattern (`ISDB_RS_` prefix, skip when
unset, never fail for missing data).

## Development setup

- **Rust**: install [rustup](https://rustup.rs/); `rust-toolchain.toml`
  selects the pinned toolchain (with rustfmt and clippy) automatically. The
  minimum supported Rust version is `rust-version` in `Cargo.toml` (1.88);
  `mise run msrv` needs it installed: `rustup toolchain install 1.88 --profile minimal`.
- **libhackrf** (2022.09.1 or later; older releases are refused at open):
  needed only for the `hackrf` feature of `isdb-radio` (forwarded by the
  `hackrf` feature of `isdb-cli`), which is on by default and links the
  system library even when no radio is attached (Arch `hackrf`,
  Debian/Ubuntu `libhackrf-dev`, Homebrew `hackrf`).
- **libiio** (0.x API, 0.21 or later; libiio 1.x is not supported): needed
  only for the `pluto` feature of `isdb-radio` (forwarded by the `pluto`
  feature of `isdb-cli`), also on by default (Arch `libiio`,
  Debian/Ubuntu `libiio-dev`, Fedora `libiio-devel`, Homebrew `libiio`).
- `cargo build -p isdb-cli --no-default-features` builds without either
  library; CI checks that build, and `isdb-radio` without any backend, in
  the `no-radio-libs` job.
- **mise** (task runner and harness tools): install
  [mise](https://mise.jdx.dev/), then run `mise install` in the repository.
  It installs the pinned node/pnpm (commitlint), lefthook, cargo-deny,
  actionlint, zizmor, pinact and shellcheck, runs `pnpm install` and installs
  the git hooks (`lefthook install`). Every check is a mise task
  ([Checks](#checks)); the Rust tasks are plain cargo/rustup underneath.
- Without the pinned harness tools: `mise run --skip-tools <task>` does not
  install missing tools and uses whatever is on `PATH`, so
  `cargo install --locked cargo-deny` is enough for every Rust task; the git
  hooks then need lefthook and pnpm installed by hand.

### Git hooks

Managed by lefthook (`lefthook.yaml`, installed into `.git/hooks` by
`mise install` or `lefthook install`):

| Hook | Runs |
|---|---|
| `pre-commit` | `mise run fmt` on staged `*.rs` (re-staged), `mise run clippy` when Rust files or manifests change, `mise run deny-offline` when manifests or `deny.toml` change, actionlint / zizmor / pinact on workflow changes, `mise lock` on `mise.toml` changes |
| `commit-msg` | commitlint (Conventional Commits) |
| `pre-push` | refuses direct pushes to `main` |

Skip once with `LEFTHOOK=0 git commit …` (CI runs the same checks anyway).
In a linked git worktree (`git worktree add`), lefthook's handling of
partially staged files fails; stage whole files, commit from the main
checkout, or skip the hook once and run `mise run lint` yourself.

### Checks

mise is the single task runner (tasks in `mise.toml`) and CI runs the same
tasks; `mise tasks` lists them with their descriptions. The tasks that
`check` and `lint` depend on run in parallel (up to mise's `jobs` setting).

| Command | What it does |
|---|---|
| `mise run check` | everything CI runs (below) |
| `mise run lint` | `fmt-check` + `clippy` |
| `mise run fmt` / `mise run fmt-check` | rustfmt (workspace and `oracle/rust_tx3`) |
| `mise run clippy` | clippy on all targets, `-D warnings` |
| `mise run test` | unit, integration and doc tests (ignored tests excluded) |
| `mise run test-release` | the same in release (faster PHY loopbacks) |
| `mise run test-ignored` | heavy stress/throughput tests, release (not in CI) |
| `mise run doc` | rustdoc with `-D warnings` |
| `mise run deny` | cargo-deny: advisories, bans, licences, sources |
| `mise run deny-offline` | the same without the advisory database fetch (pre-commit) |
| `mise run msrv` | `cargo +<rust-version> check` on every target |
| `mise run oracle` | clippy on the stand-alone `oracle/rust_tx3` helper |

Lints are configured once in `[workspace.lints]` (`Cargo.toml`); every crate
opts in with `[lints] workspace = true`. `unsafe_code` is denied everywhere
except the FFI crate `isdb-hackrf`, which allows it in `src/lib.rs`. Do not
add `#[allow(...)]` to silence a lint without a comment that says why.

New dependencies must pass `mise run deny` (crates.io only, licences compatible
with Apache-2.0) and build with the MSRV. Raising the MSRV is a deliberate
change: say so in the PR and in the changelog. A dependency on another
workspace crate carries `version` next to `path` (`mise run deny` bans
wildcards), so `cargo package --workspace` works; the one exception is a
path-only dev-dependency that would otherwise form a publish cycle
(isdbt-mux → isdb-analyze).

### Oracle checks

`oracle/` holds the differential test against GNU Radio gr-isdbt, an
external GPL-3.0 program that is **not** distributed here and must not be
vendored or copied. The scripts are Apache-2.0 like the rest of the
repository, but `grisdbt_tx.py` and `grisdbt_rx.py` import GNU Radio and
gr-isdbt at run time, so the running combination is under GPL-3.0
([oracle/README.md](oracle/README.md)). Run it when you change
`isdbt-fec`, `isdbt-ofdm` or `isdbt-phy` behaviour:

```sh
cargo build --release -p isdbt-phy --examples
cargo build --release --manifest-path oracle/rust_tx3/Cargo.toml --target-dir target/oracle
python3 oracle/run_matrix.py        # rows 1-8, about 2 minutes
```

The scripts run gr-isdbt in a container built from
[`oracle/Dockerfile`](oracle/Dockerfile) (GNU Radio 3.10, gr-isdbt at a
pinned commit) with the repository mounted at `/work`; build and start it
as described in [docs/test-data.md](docs/test-data.md#the-gr-isdbt-oracle).
The container name defaults to `isdb-oracle` (override with
`ISDB_RS_ORACLE_CONTAINER`); results go to `target/oracle-matrix/`
(`ISDB_RS_ORACLE_OUT`, which must lie inside the repository). Full
reproduction steps and the current results are in
[VERIFICATION.md](VERIFICATION.md). A disagreement with the oracle is an
investigation, not a bug report against either side: settle it with the
spec and record the outcome in SPEC-NOTES / VERIFICATION.md.

## Commits and pull requests

- Commit messages follow [Conventional Commits](https://www.conventionalcommits.org/)
  (`feat:`, `fix:`, `docs:`, `test:`, `refactor:`, `perf:`, `chore:`,
  `ci:` …). The optional scope is a crate directory name (`isdb-ts`,
  `isdbt-ofdm`, …) or `oracle`, `workspace`, `ci`, `deps`. commitlint
  enforces this in the hook and in CI.
- Work on a branch and open a pull request; `main` is merged by squash.
  CI (`CI` and `Lint` workflows) must be green.
- Add a line under `## [Unreleased]` in [CHANGELOG.md](CHANGELOG.md) for
  user-visible changes.
- Update the crate README and SPEC-NOTES in the same PR as the behaviour
  they describe.

## Reporting security issues

Do not open public issues for vulnerabilities; see [SECURITY.md](SECURITY.md).
